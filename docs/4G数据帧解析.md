## 1. 模块的两种串口数据

### 1.1 MQTT 分发模式数据：`num,payload`

模块工作在 **MQTT 分发模式**（`AT+MQTTMOD` ≠ 透传）时，串口与网络之间用
**主题序号 + 逗号** 区分数据（手册原文：*“接收下发数据时，数据格式为 num,payload，
num 即为预设主题指令 AT+MQTTSUBTP 中的参数 subnum”*）：

| 方向 | 格式 | num 含义 |
| --- | --- | --- |
| 串口 → 模块（发布） | `num,payload` | 发布主题号 1~10（`AT+MQTTPUBTP`） |
| 模块 → 串口（订阅） | `num,payload` | 订阅主题号 1~10（`AT+MQTTSUBTP`） |
| 临时主题（两者） | `0,flag,topic,qos[,retain],payload` | 0 = 临时主题 |

本产品的订阅主题（`AT+MQTTSUBTP` 查询结果）：

| num | 主题 | 用途 | 本工程处理 |
| --- | --- | --- | --- |
| 1 | `ai_safety/ais011/system/server/hook` | 云端 → 设备命令（远程调试口，等同 shell 串口） | `craner#AT...` 本机命令 / `usr.cn#AT...` 转模块 |
| 2 | `ai_safety/ais011/ota/server/hook` | （已废弃）云端 → 设备 OTA 数据 | 忽略并回显告警：固件改走 HTTP（`AT+OTADL`），本话题只用于设备→云端上报结果 |
| 3 | `ai_safety/ais011/command/device_manager/hook` | 云端 → 设备管理命令 | 0xA5 二进制协议解析器 |
| 4 | `ai_safety/ais011/heartbeat/device_manager/hook` | 云端 → 设备心跳 | 同上（解析器/忽略） |
| 5~10 | `/SubTopicN`（未启用） | 预留 | 同上（解析器/忽略） |

发布主题（`AT+MQTTPUBTP`）：1 = system（设备应答）、2 = ota（设备→云端的 OTA 结果）、
3 = inform（设备上报），其余未启用。因此 MCU 侧发送时使用前缀 `1,` / `2,` / `3,`。

### 1.2 模块自身 AT 指令/应答

`usr.cn#` 是模块的 **命令字（命令密码）**，默认值即 `AT+CMDPW` 的默认值 `usr.cn#`，
串口 AT 与网络 AT 都是 `命令字 + 指令`，例如 `usr.cn#AT+VER`（以 `[CR]`/`[CR][LF]` 结束）。

应答格式（AT 指令集统一格式，**有明确结束标记**）：

```text
{CR}{LF}+<命令名>:<参数>{CR}{LF}
{CR}{LF}OK{CR}{LF}            ← 或 {CR}{LF}ERROR{CR}{LF}
```

因此**模块 AT 应答可以可靠地“收完整帧再处理”**：以 `OK`/`ERROR` 作为结束判断，
必要时用超时兜底。

## 2. 关键结论：一帧可能被拆成多个串口块

模块把一条应答/一个 payload 通过 UART 发出时，可能在内部按行/按批输出，
中间出现大于串口空闲判定时间的间隔，于是 MCU 侧会把它收成**多个串口块**。

实测：`usr.cn#AT+MQTTPUBTP` 的完整应答 **349 字节 / 9 个块**（`4g rx 54 B
(frames=9 bytes=349 drops=0)`），PC 直连模块看到的是完整 11 行 + `OK`。

所以分发**不能只看单个串口块的首字节**，必须：

1. **AT 应答**：发命令后开始累积，直到 `OK`/`ERROR` 结束标记（或 3 s 超时），
   再把整段应答按一个完整帧处理；
2. **MQTT payload**：记住该块路由到的消费者（OTA / 管理协议），后续没有
   `num,` 前缀的续块继续喂给同一消费者（粘滞 1 s）；
3. 允许“块首字节恰好是数字”的情况不再误判（按 `0~10` + `,` 完整解析前缀）。

## 3. 本工程的分发流程（app/hook_4g/hook_4g.c）

```text
收到一个串口块
  ├─ 1) 解析 "<num>," 前缀（num = 0~10）
  │      num=1 → craner#AT 命令 → 本机执行；否则 usr.cn#AT → 转发给模块
  │      num=2 → OTA：忽略并告警（该话题已改为设备→云端，固件走 HTTP 下载）
  │      其他  → 管理/遗留数据：喂给 0xA5 协议解析器（可打印文本同时回显）
  ├─ 2) 无前缀且正在等待 AT 应答 → 累积，直到 OK/ERROR 或超时 → 一次性打印 + 发布到主题 1
  ├─ 3) 无前缀但距上次路由 <1 s → 续块：继续喂给上次的消费者（0xA5 协议解析器）
  ├─ 4) 以 "usr.cn#" 开头或纯文本 → 打印到 shell
  │      命令回显 "usr.cn#AT..." 和开机 banner "WH-LTE-7S1" 只进控制台/日志；
  │      模块的真正应答（+WKMOD / OK / +CSQ ...）仍镜像到主题 1
  └─ 5) 其它（二进制、无前缀）→ 0xA5 协议解析器，并打印一行限速 hex 头部便于排查
```

与原 `uart_4g_recv_callback` 的对应关系：

| 原实现（CubeMX/FreeRTOS） | 本工程（Zephyr） |
| --- | --- |
| `buf[0]=='1'` → craner#/usr.cn# 命令处理 | 解析 `num=1` 后调用同一套 AT 处理函数 |
| `buf[0]=='2'` → 写入 OTA ring，供 Ymodem 解析 | 已删除：`num=2` 只用于设备→云端上报，收到即忽略并告警 |
| `buf[0]=='3'/'4'` → 写入 ring，线程解析 0xA5 协议 | `num=0,3~10` → `hook_cloud_proto_feed()` |
| `usr.cn#` 开头 → shell + 发布主题 1 | 保留（纯文本/usr.cn# 同样处理），并支持**跨块累积** |
| 其它 → 写入 ring 交给线程解析 | 保留（0xA5 解析器），无前缀续块按粘滞路由 |
| 以空闲定时器切块后按块首字节判断 | 增加 AT 应答重组 + payload 粘滞路由，保证“完整帧再判断” |

## 4. 调试用的观测手段

> 修复记录（本次）：`component/uart_manage` 的 Zephyr 移植版里 `rx_idx` 是
> `uint8_t`，而 4G 通道接收缓冲是 2048 字节 —— 任何超过 255 字节的帧都会索引回绕，
> **用帧尾覆盖帧头**，空闲回调按回绕后的长度上报，表现就是“只收到尾部”。
> 该索引已改为 `uint16_t`；同时新增可选的 bounce buffer（`recv_buffer_alt`），
> 空闲回调在短临界区内把整帧拷到 bounce buffer 后再交给上层，避免 UART 中断在
> 拷贝期间把新字节写回 `recv_buffer[0]` 覆盖帧头。
>
> 后续（问题点汇总 1）：GPS 通道已随 GPS 模块一起删除，`hook usr AT+Z` 之类的
> 模块命令也不再周期性发送（该命令会让模组重启）。

```text
hook usr hex on            # 打开逐帧 hex dump（同时清零收发计数）
hook usr mqtt_pub_tp       # 快捷查询 MQTT 发布话题（= hook usr AT+MQTTPUBTP）
hook usr AT+MQTTPUBTP      # 也可直接发原始模块命令（应答会自动重组后打印）
hook usr hex off           # 关闭
```

`hook usr` 预置的快捷查询（等价于后面括号里的原始 AT 指令）：

| 快捷命令 | 模块指令 |
| --- | --- |
| `hook usr wk_mod` | `AT+WKMOD` |
| `hook usr mqtt_pub_tp` | `AT+MQTTPUBTP` |
| `hook usr mqtt_sub_tp` | `AT+MQTTSUBTP` |
| `hook usr mqtt_sta` | `AT+MQTTSTA` |
| `hook usr mqtt_svr` | `AT+MQTTSVR` |
| `hook usr mqtt_user` | `AT+MQTTUSER` |
| `hook usr mqtt_psw` | `AT+MQTTPSW` |
| `hook usr mqtt_cid` | `AT+MQTTCID` |

本机 `craner#AT` 命令统一走 `hook craner <命令>`（例如 `hook craner AT+OTAINFO`）；
`hook usr` 只负责 4G 模块自身的指令，两者职责分开。

## 4. MQTT 话题自动组建（app/hook_4g_cfg）

出厂不再需要工程师逐条敲 `usr.cn#AT...`。每次 MCU 开机时
`app/hook_4g_cfg/` 执行一次配置流程（**只在开机时，运行中改参数不触发**）：

```text
等模块应答（探测 AT+WKMOD，最多 60 s：冷启动 + 注网，实测首次应答约 40 s）
  ├─ 不应答 → 写日志，下次开机再试（不清配置）
  ├─ AT+WKMOD 读回不含 "MQTT" → 出厂流程：AT+CLEAR → 全量下发 → AT+S
  └─ AT+WKMOD 是 "MQTT,NOR" → 逐项读回比对
       ├─ 全部一致 → 结束（不写模块 flash）
       └─ 有差异 → 只写差异项 → AT+S
AT+S 保存并让模块重启（MCU 不重启）→ 等模块回来 → AT+MQTTSTA 校验 CONNECTION
写完后再读回比对一次：模块在写入过程中若自行重启，重启期间发出的命令会丢失，
只校验 MQTT 连接会漏掉这种"报成功但配置不全"的情况。
```

写命令或校验失败会重试 3 次（每次之间 2 s）；探测超时只记录一次，不做重试。

校验结果分两级处理：

* **读回比对仍有差异** → 配置问题，重试整个流程（最多 3 次）；
* **读回一致但 `AT+MQTTSTA` 未连接** → 网络问题，再给一整轮机会；仍连不上就记
  `configuration stored but MQTT not connected` 并按成功结束（现场没信号时重试没有意义）。

话题与 CID 由持久化参数 `device.no` 推导（`dev = "ais" + device.no`）：

```text
CID    = <dev>-hook                                       ais998-hook
PUB 1  = ai_safety/<dev>/system/hook/server               2,0
PUB 2  = ai_safety/<dev>/ota/hook/server                  2,0
PUB 3  = ai_safety/<dev>/inform/hook/device_manager       2,0
SUB 1  = ai_safety/<dev>/system/server/hook               2
SUB 2  = ai_safety/<dev>/ota/server/hook                  2
SUB 3  = ai_safety/<dev>/command/device_manager/hook      2
SUB 4  = ai_safety/<dev>/heartbeat/device_manager/hook    0
```

其余下发的配置项：`AT+WKMOD=MQTT,NOR`、`AT+MQTTMOD=1`、`AT+MQTTCFG=60,1`、
`AT+MQTTSVR=<mqtt.svr>,<mqtt.port>`、`AT+MQTTUSER`、`AT+MQTTPSW`、
`AT+HEARTEN=OFF`、`AT+REGEN=OFF`、`AT+RSTIM=0`（最后三项关掉模块自身的
心跳包、注册包与定时重启，`RSTIM=0` 正是问题点汇总 1 里"模块每小时重启"的开关）。

`device.no` 与 `mqtt.svr/port/user/psw` 都是参数表里的持久化参数：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `device.no` | 硬件 `short_id` | 话题中的设备号，`ais` 前缀在拼装时加 |
| `mqtt.svr` | `mqtt.craner.hk` | MQTT 服务器 |
| `mqtt.port` | `1883` | MQTT 端口 |
| `mqtt.user` | `hkcrctest` | MQTT 用户名 |
| `mqtt.psw` | `crcHK3130` | MQTT 密码（日志与远端读取一律显示 `***`） |
| `modem.cfg_hash` | 空 | 已下发参数集的指纹（程序维护），变化即触发一次重配 |

现场与云端命令：

```text
hook provision status    # 期望的话题/CID 与当前状态
hook provision run       # 比对 + 差异写入（模块重启，10~40 s）
hook provision factory   # AT+CLEAR + 全量重写（新模块/换模块）

craner#AT+PARAM                  # 云端列举参数（话题 1）
craner#AT+PARAM=device.no         # 读单个
craner#AT+PARAM=device.no,998     # 写（内存，dirty）
craner#AT+PARAM=device.no,998,save # 写并落盘
craner#AT+PARAM=save              # 保存所有 dirty
craner#AT+PARAM=reset,device.no   # 恢复默认
```

整个过程使用同步 AT 通道（`hook_4g_at_cmd()`），交换内容不打印到终端、也不镜像到
话题 1 —— 因为其中包含 MQTT 密码；配置期间的决策与结果只写入离线日志的 `4g` 分类。

日志中每帧一行：

```text
<inf> hook_4g: 4g rx 43 B (frames=1 bytes=43 drops=0)
<inf> hook_4g: 0000: 2B 4D 51 54 54 50 55 42 54 50 3A 0D 0A ...
```

- `frames` / `bytes`：自打开 hex（或上电）以来收到的块数与字节数；
- `drops`：环形缓冲/帧长度队列满而丢弃的块数，正常应为 0；
- 若出现 `4g uart error flags 0x..`，说明串口层出现 ORE/FE/PE 错误（硬件层丢字节），
  需要检查波特率、线缆、或改用 FIFO/DMA 接收。
