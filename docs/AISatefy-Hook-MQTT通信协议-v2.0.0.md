# AISatefy-Hook-MQTT通信协议-v2.0.0

> 修订版（2026-08-26）：依据当前代码分支 `release/V2_1_1-app0` 重新核对，重点修订“应答帧”部分，修订内容见文末“修订记录”。

## 1. 协议概述

1. **通讯原则**：为防止 4G 模组串口粘包，单片机不主动上报电量等业务数据，采用“`上位机主动询问 -> 设备被动回复`”的问答模型，由 STM32 应答。
2. **询问帧判断**：以内容 ID 和数据长度区分读/写。`DATA-LEN == 0` 为读询问帧；`DATA-LEN > 0` 为写指令帧。
3. **应答原则**：
   - 读指令返回信息帧（原内容 ID，数据段非空）；
   - 写指令返回应答帧（原内容 ID，数据段为空）；
   - 处理异常时返回错误帧（内容 ID 最高位置 1，数据段为 1 字节错误码）；
   - 例外：0x05 工作心跳的写指令不产生应答；0xF0 系统错误码的写指令无处理、无应答；0x08 数据长度不足的写指令不产生应答（见各命令说明）。
4. **数据包限制**：4G 模组串口断帧时间设置为 20 ms（模组侧配置）；`DATA-LEN` 为 1 字节，数据段最大 255 字节，整帧（SOF..CRC）最长 260 字节。

## 2. MQTT 主题

| 主题 | 方向 | 用途 |
|---|---|---|
| `ai_safety/ais001/command/device_manager/hook` | 上位机 -> 吊钩模组 | 指令主题，发布 0xA5 帧体 |
| `ai_safety/ais001/inform/hook/device_manager` | 吊钩模组 -> 上位机 | 应答/通知主题 |
| `ai_safety/ais001/heartbeat/device_manager/hook` | 上位机 -> 吊钩模组 | 工作心跳主题（0x05 心跳帧，1 Hz） |

### 2.1 固件更新（HTTP + OTA）

固件更新**不占用 0xA5 协议**，全部走 topic 1 的 `craner#AT...` 命令，
与 `AT+OTAINFO` / `AT+OTACONFIRM` 同一条通道（详见 README 第 15 条）：

| 命令 | 作用 |
| --- | --- |
| `craner#AT+OTADL=<url>` | 下载固件：4G 模块切 HTTPD 拉取 URL，流式写入 slot1，完成后切回 MQTT |
| `craner#AT+OTATEST=<hash8>` | 安装 hash 指定的镜像（必须是 slot1 那份）+ MCUboot test 升级并重启；hash 不存在/不在 slot1 时回 `craner#AT+OTATEST ... ERROR` |
| `craner#AT+OTAINFO` | slot0/slot1 版本 + 8 位 hash + 状态位，以及 HTTP 下载状态 |
| `craner#AT+OTACONFIRM` | 确认运行中的测试镜像（1 小时内不确认会回滚） |

> 旧的 MQTT + Ymodem 下发链路（`AT+OTAREQUEST` / `AT+OTABOOT`、`+OTASTATE` 行）
> 已删除：它与 HTTP 下载抢同一个模块、同一条链路和同一套 slot1 状态。
> `AT+OTACANCEL` 也随之删除（不再有"暂存状态"需要撤销）。

`AT+OTAINFO` 的应答：

```text
craner#+OTAINFO:slot0=<版本>,<hash8>[,active][,confirmed]:slot1=<...>
craner#+OTAHTTP:<0 idle|1 downloading|2 ready|3 error>,<written>,<expected>
```

`+OTAHTTP` 是 HTTP 下载（`AT+OTADL`）的状态；`<hash8>` 是各 slot 镜像 SHA-256
的前 8 位，就是 `AT+OTATEST=<hash8>` 的入参。

**下载结果上报（topic 2，设备 -> 云端）**：下载结束并切回 MQTT 后，设备在
`ai_safety/<dev>/ota/hook/server`（OTA 专用通道，设备 -> 云端，云端不再向这条
话题下发任何数据）发布一行结果，云端据此决定是否下发 `AT+OTATEST`。
**云端需订阅该话题**；命令应答
仍在 topic 1（`system/hook/server`）。

```text
+OTADL:OK,<响应体字节>,<镜像字节>,v<版本>,<hash 前 8 位>
+OTADL:ERR,<原因>,<已收字节>,<期望字节>
原因：1 URL 非法、2 模块切换 HTTPD 失败、3 无响应数据、4 接收/写入/校验失败
```

只发**一条**、只走 topic 2：模块会把连续无间隔（20 ms 断帧时间）发出的串口数据
合并成一条 MQTT 消息，并且只认第一个通道前缀，所以同时在 topic 1 和 topic 2
各发一份，云端会收到两条内容粘在一起的内容（实测 2026-09-24 18:01）。

**安装不依赖任何持久化状态**：`AT+OTATEST` 的判据就是"slot1 里那份镜像的
SHA-256 前缀"，全部来自 Flash，与设备的 RAM 状态无关，所以"已下载、未安装"
期间断电或复位后，重启直接用 `AT+OTATEST=<hash8>` 仍然可以安装，
**不需要重新下载**，也不需要曾经下发过 `AT+OTADL`。hash 可从下载结果
（`+OTADL:OK,...,<hash8>`）或 `AT+OTAINFO` 得到；运行中的 slot0 无法被选中。

流程要点：`AT+OTADL` 期间设备脱离 MQTT（模块切到 HTTPD），下载结束后**自动切回
MQTT 并继续运行旧镜像**（`+OTAHTTP:2,...` 表示镜像已写入 slot1 并通过校验），
直到收到 `AT+OTATEST` 才武装 MCUboot 测试升级并重启——这样设备在"已下载、未安装"
期间始终可以通过 MQTT 访问。

URL 要求：明文 `http://host[:port]/path`、≤ **200 字节**、服务器返回
`200` + `Content-Length`（不支持 302 重定向和 `chunked`）。

> 说明：`mqtt_tester.py` 中命令主题发布的是纯 0xA5 帧体（无前缀）；应答帧在 MCU 发给 4G 模组时带 `3,` 前缀，MQTT 消息体是否保留该前缀取决于 4G 模组固件/平台网关配置，现场以实测为准。

## 3. 通信链路与消息前缀（MCU <-> 4G 模组串口）

平台命令经 4G 模组转发到 MCU（USART1，115200）时，消息体可能带有以下前缀，MCU 按前缀路由：

| 前缀 | 处理 |
|---|---|
| `1,` | 按 AT 命令处理（`craner#` / `usr.cn#`），AT 应答同样以 `1,` 前缀回发 |
| `2,` | 4G 模组自身应答，MCU 忽略 |
| `3,` / `4,` | 去掉前缀后进入 4G 业务帧解析器（0xA5 帧体） |
| `usr.cn#...` | 透传：原样转发到调试串口 Shell，同时经 MQTT 回发 |

MCU 上行到 4G 模组：

| 前缀 | 内容 | 对应主题 |
|---|---|---|
| `3,` + 帧体 | 业务应答帧/通知帧 | 应答/通知主题 |
| `1,` + AT 应答 | AT 命令应答（如 `craner#OK`） | AT 应答主题 |

> **本工程改动（2026-09，问题点汇总 1 第 2 条）**：已删除每 60 分钟一次的
> `usr.cn#AT+Z` 保活命令。实测该命令会让 4G 模组重启，链路保活改由模组/云端负责
> （后续再优化）。因此 4G 链路上不再有周期性模组命令，只有业务帧与模块自身应答。

## 4. 帧格式

帧内多字节字段统一使用**小端序**。

### 4.1 读指令请求帧结构（数据段为空）

| 字段 | 长度 | 说明 |
|---|---|---|
| SOF | 1 字节 | 帧起始字节，固定 `0xA5` |
| SEQ | 1 字节 | 包序号，上位机循环递增（0~255） |
| CMD_ID | 1 字节 | 内容 ID |
| DATA-LEN | 1 字节 | 读指令无数据段，固定为 0 |
| CRC16 | 2 字节 | 整包校验值（小端序发送） |

### 4.2 读指令应答帧结构（原内容 ID，数据段非空）

| 字段 | 长度 | 说明 |
|---|---|---|
| SOF | 1 字节 | 帧起始字节，固定 `0xA5` |
| SEQ | 1 字节 | **设备侧独立计数**（`g_tx_seq`），每发送一帧自增 1，循环 0~255，**不回显请求帧 SEQ** |
| CMD_ID | 1 字节 | 内容 ID，与请求帧相同 |
| DATA-LEN | 1 字节 | 数据段长度 |
| DATA | N 字节 | 数据段（各命令格式见第 6 节） |
| CRC16 | 2 字节 | 整包校验值（小端序发送） |

### 4.3 写指令请求帧结构（数据段非空）

| 字段 | 长度 | 说明 |
|---|---|---|
| SOF | 1 字节 | 帧起始字节，固定 `0xA5` |
| SEQ | 1 字节 | 包序号，上位机循环递增（0~255） |
| CMD_ID | 1 字节 | 内容 ID |
| DATA-LEN | 1 字节 | 数据段长度 |
| DATA | N 字节 | 数据段 |
| CRC16 | 2 字节 | 整包校验值（小端序发送） |

### 4.4 写指令应答帧结构（原内容 ID，数据段为空）

| 字段 | 长度 | 说明 |
|---|---|---|
| SOF | 1 字节 | 帧起始字节，固定 `0xA5` |
| SEQ | 1 字节 | **设备侧独立计数**，不回显请求帧 SEQ |
| CMD_ID | 1 字节 | 内容 ID，与请求帧相同 |
| DATA-LEN | 1 字节 | 固定为 0 |
| CRC16 | 2 字节 | 整包校验值（小端序发送） |

### 4.5 错误帧结构（内容 ID 最高位置 1，数据段为错误码）

| 字段 | 长度 | 说明 |
|---|---|---|
| SOF | 1 字节 | 帧起始字节，固定 `0xA5` |
| SEQ | 1 字节 | **设备侧独立计数**，不回显请求帧 SEQ |
| CMD_ID | 1 字节 | 请求帧内容 ID 的最高位置 1，例如 0x01 的错误帧 CMD_ID 为 0x81 |
| DATA-LEN | 1 字节 | 固定为 1 |
| DATA | 1 字节 | 错误码（1=CRC 校验失败、2=帧长度异常（保留）、3=未知内容 ID、4=不可读取/写入） |
| CRC16 | 2 字节 | 整包校验值（小端序发送） |

### 4.6 应答帧关键规则（重点）

1. **SEQ 不回显**：当前代码中设备使用自己的发送计数器 `g_tx_seq`，每发送一帧应答自增 1（0~255 循环），与请求帧 SEQ 无关。上位机不能依赖 SEQ 回显做帧配对，应使用 CMD_ID + 请求/应答内容关联。
2. **CRC 覆盖范围**：`SOF + SEQ + CMD_ID + DATA-LEN + DATA`（即从帧头到数据段结束，不含 CRC 本身）。
3. **CRC 字节序**：低字节在前、高字节在后（小端序）。
4. **应答前缀**：应答帧在 MQTT 消息体中带 `3,` 前缀（见第 3 节）。
5. **错误帧触发场景**：CRC 校验失败、未知内容 ID、只读命令收到写指令（0x02/0x06）等。

CRC16 计算函数：

```c
// CRC16-CCITT (poly 0x1021) initial 0x0000
static uint16_t crc16_ccitt(const uint8_t *buf, uint32_t len)
{
    uint16_t crc = 0;
    for (uint32_t i = 0; i < len; ++i)
    {
        crc ^= (uint16_t)buf[i] << 8;
        for (uint8_t j = 0; j < 8; ++j)
        {
            if (crc & 0x8000)
                crc = (uint16_t)((crc << 1) ^ 0x1021);
            else
                crc <<= 1;
        }
    }
    return crc;
}
```

## 5. 内容 ID 说明

| 内容 ID | 说明 | 读应答 | 写处理 | 写应答 |
|---|---|---|---|---|
| 0x01 | 声光报警控制 | 1 字节状态 | 执行灯光/喇叭/音量设置 | 空应答 |
| 0x02 | 电池信息 | 12 字节 | 只读，拒绝写入 | 错误帧 0x82，错误码 0x04 |
| 0x03 | 保留（未实现） | 按未知 ID 处理 | 按未知 ID 处理 | 错误帧 0x83，错误码 0x03 |
| 0x04 | 是否使能工作心跳 | 1 字节 | 设置使能 | 空应答 |
| 0x05 | 工作心跳 | 1 字节 | 更新心跳值 | **无应答** |
| 0x06 | 工作模式 | 2 字节 | 只读，拒绝写入 | 错误帧 0x86，错误码 0x04 |
| 0x07 | 是否使能睡眠模式（自动开关机） | 1 字节 | 设置使能 | 空应答 |
| 0x08 | 睡眠时间（自动开关机） | 4 字节 | 设置开关机时间（数据 >= 4 字节） | 空应答（数据 < 4 字节无应答） |
| 0x09 | 当前时间 / 校准 | 6 字节 | 写 RTC 校准寄存器（数据 = 6 字节，3 个小端 u16：年 / 月日 / 时分） | 写应答；长度错误返回 `0x02`，数值非法返回 `0x04` |
| 0xF0 | 系统错误码 | 1 字节 | 无处理 | 无应答 |

## 6. 数据帧定义

### 6.1 0x01 声光预警灯

写指令数据（1 字节）与读应答数据（1 字节）布局一致：

| Bit | 说明 |
|---|---|
| Bit 0 | 爆闪灯（1=开 / 0=关） |
| Bit 1 | 7 米音频（1=响 / 0=停） |
| Bit 2 | 3 米音频（1=响 / 0=停） |
| Bit 3~7 | 音量（0~30 档，默认 30） |

读应答按当前内部状态组装：Bit 0 取爆闪灯状态寄存器；Bit 1 取喇叭状态（=7 米）；Bit 2 取喇叭状态（=3 米）；Bit 3~7 取当前音量寄存器的低 5 位。

```c
#pragma pack(1)
typedef struct {
    uint8_t light_on  : 1; // Bit 0: 爆闪灯 (1开/0关)
    uint8_t sound_7m  : 1; // Bit 1: 7米报警 (1开/0关)
    uint8_t sound_3m  : 1; // Bit 2: 3米报警 (1开/0关)
    uint8_t volume    : 5; // Bit 3-7: 音量 (0~30)
} sound_light_cmd_t;
#pragma pack()
```

### 6.2 0x02 电池信息

读应答数据共 12 字节，全部小端序：

| 字节偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 电量 | 2 字节 | `uint16` | 0~10000，10000 代表 100% 电量 |
| 2 | 总电压 | 2 字节 | `uint16` | 单位：0.01V |
| 4 | 总电流 | 2 字节 | `uint16` | 单位：0.01A（设备侧按绝对值上报，充/放电方向见说明） |
| 6 | 剩余放电时间 | 2 字节 | `uint16` | 单位：min；充电中该值为 0xFFFF |
| 8 | 剩余充电时间 | 2 字节 | `uint16` | 单位：min；放电中该值为 0xFFFF |
| 10 | 电池保护状态 | 2 字节 | `uint16` | 见下方位定义 |

保护状态位定义（bit0~bit14 为 1 表示发生保护）：

| Bit | 含义 |
|---|---|
| 0 | 单体过压保护 |
| 1 | 单体欠压保护 |
| 2 | 整组过压保护 |
| 3 | 整组欠压保护 |
| 4 | 充电过温保护 |
| 5 | 充电低温保护 |
| 6 | 放电过温保护 |
| 7 | 放电低温保护 |
| 8 | 充电过流保护 |
| 9 | 放电过流保护 |
| 10 | 短路保护 |
| 11 | 前端检测 IC 错误 |
| 12 | 软件锁定 MOS |
| 13 | 断线告警 |
| 14 | 二次过压告警 |
| 15 | 自锁开关状态（0=闭合，1=断开） |

> 说明：充/放电状态由设备内部电流符号判断（负=放电、正=充电、零=静止），当前 12 字节应答中未直接包含该状态位；上位机可通过电流值与剩余时间字段推断。

```c
#pragma pack(1)
typedef struct {
    uint16_t battery;              // 电量 0~10000 (10000=100%)
    uint16_t voltage;              // 总电压 0.01V
    uint16_t current;              // 总电流 0.01A (绝对值)
    uint16_t remain_discharge_min; // 剩余放电时间 min，充电时为 0xFFFF
    uint16_t remain_charge_min;    // 剩余充电时间 min，放电时为 0xFFFF
    uint16_t protect_status;       // 保护状态，位定义见上表
} bms_status_payload_t;
#pragma pack()
```

### 6.3 0x04 是否使能工作心跳

| 字节偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 工作心跳使能 | 1 字节 | `uint8` | 1=开启（默认开启）；0=关闭 |

```c
typedef struct {
    uint8_t heartbeat_en;
} heart_beat_en_t;
```

### 6.4 0x05 工作心跳

| 字节偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 工作心跳 | 1 字节 | `uint8` | 上位机 1 Hz 递增发送（0~255 循环），值发生变化即视为在线 |

```c
typedef struct {
    uint8_t heartbeat;
} heart_beat_t;
```

心跳保护行为（与当前代码一致）：

- 心跳使能默认开启（寄存器 117 = 1）。
- 心跳值发生变化即认为上位机在线，声光电源保持上电。
- **10 秒**未收到新心跳：清除爆闪灯和喇叭控制命令（静默，声光不断电）。
- **60 秒**未收到新心跳：关闭声光模块电源、拉低 `PWD_LED`，并设置系统错误码 Bit0（心跳超时）。
- 心跳恢复后：重新上电、恢复音量同步并清除心跳超时错误。
- 关闭心跳检测后：声光电源保持上电，不受心跳影响。

### 6.5 0x06 工作模式

读应答共 **2 字节**：

| 字节偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 工作模式 | 1 字节 | `uint8` | 0=待机，1=正常通信，2=低电量（电量 <= 2000，即 20%），3=设备异常 |
| 1 | 错误码 | 1 字节 | `uint8` | 仅当工作模式为 3（设备异常）时携带当前系统错误码，否则为 0 |

```c
#pragma pack(1)
typedef struct {
    uint8_t work_mode;  // 0 待机 / 1 正常 / 2 低电量 / 3 设备异常
    uint8_t error_code; // 仅 mode==3 时有效，携带系统错误码
} work_mode_status_t;
#pragma pack()
```

### 6.7 0x08 睡眠模式（自动开关机）时间

读应答共 4 字节，小端序：

| 字节偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 开机时间 | 2 字节 | `uint16` | 默认 06:00（0x0600） |
| 2 | 关机时间 | 2 字节 | `uint16` | 默认 21:00（0x1500） |

时间格式：高字节=小时 / 低字节=分钟，例如 `0x1500` = 21:00。

```c
#pragma pack(1)
typedef struct {
    uint16_t on_time;  // 开机时间 HHMM
    uint16_t off_time; // 关机时间 HHMM
} sys_schedule_time_t;
#pragma pack()
```

写指令需携带 4 字节数据；数据不足 4 字节时当前代码不产生应答。

### 6.8 0x09 当前时间/时间校准

> **本工程改动（2026-09，问题点汇总 1 第 3 条）**：本产品已取消 GPS，原来的
> `RTC_TIME`（只有 HHMM、既是校准输入又是时间显示）被拆成两组寄存器：
> 校准组是保持寄存器 H0x20/H0x21/H0x22（年 / 月日 / 时分，一次性命令），
> 显示组是输入寄存器 I0x10/I0x11/I0x12（年 / 月日 / 时分）。本命令的载荷随之扩展为
> **8 字节**，年-月-日-时分才能完整校准。
>
> **字段全部为小端 `uint16`**（2026-09-18 统一）：不再出现"年 2 字节 + 月/日各 1 字节 +
> 时分 2 字节"的混合编码。月与日的打包方式**和时分一致**（高位在前、低位在后），
> 也与校准寄存器 H0x21 完全相同，所以固件收到后是逐字拷贝，不需要换算。

| 字节偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 年 | 2 字节 | `uint16` 小端 | 北京时间的年份，如 2026 |
| 2 | 月:日 | 2 字节 | `uint16` 小端 | `(月 << 8) | 日`，月 1..12、日 1..31 |
| 4 | 时:分 | 2 字节 | `uint16` 小端 | `(时 << 8) | 分`，时 0..23、分 0..59 |

```c
#pragma pack(1)
typedef struct {
    uint16_t year;      // 北京时间年份（小端）
    uint16_t month_day; // (月 << 8) | 日（小端）
    uint16_t hhmm;      // (时 << 8) | 分（小端）
} current_time_t;
#pragma pack()
```

* **读**（数据段为空）：返回 6 字节，字段同上，内容为 I0x10~0x12 发布的当前北京时间。
* **写**（数据段 6 字节）：逐字段写入 RTC 校准寄存器 H0x20~0x22（与上位机 Modbus 写等价）。
  `app/hook_rtc` 线程在 1 s 内消费该命令、写入硬件 RTC 并重建 `time_manager`
  信任记录；秒被置 0，校准后由 RTC 自行走时。
* 数据长度不是 6 字节时返回错误应答 `[ID|0x80] + 0x02`（长度错误）。
* 校准值非法（年份不在 2000..2099、月/日/时分越界）时返回 `[ID|0x80] + 0x04`
  （不可读写/数值非法）并打印告警，不会写入校准寄存器。

### 6.9 0xF0 系统错误码

| 字节偏移 | 字段 | 长度 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 系统错误码 | 1 字节 | `uint8` | Bit0=心跳超时；Bit1=警报灯离线；Bit2=BMS 读取失败；多错误按位组合 |

```c
typedef struct {
    uint8_t system_error;
} sys_error_t;
```

## 7. 错误码定义

| 错误码 | 含义 | 当前代码是否主动发出 |
|---|---|---|
| 0x01 | CRC 校验失败 | 是（解析到 CRC 错误时返回） |
| 0x02 | 帧长度不够/异常 | 保留（代码中已定义，当前未主动发出） |
| 0x03 | 未知内容 ID | 是（内容 ID 无对应处理函数时返回） |
| 0x04 | 不可读取/写入 | 是（对只读命令 0x02/0x06 执行写操作时返回） |
