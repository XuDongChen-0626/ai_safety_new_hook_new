## 1. `system_health_service` 当前检测哪些健康指标

分两层看：**模块自带的内核级检查**（由 Kconfig 开关）与**本产品注册的事件表**
（`app/hook_health/hook_health.c`）。

### 1.1 本产品注册的健康事件（`hook_health_events[]`）

| 事件名 | 事件 ID | 超时 | 谁打卡 | 超时动作 |
| --- | --- | --- | --- | --- |
| `task_alive` | 1 | 12 s | 5 个业务线程在一个周期内**全部**打卡 | 日志 + `SET_DEGRADED` + `STOP_WATCHDOG_FEED` |
| `host_heartbeat` | 5 | `HEARTBEAT_TIMEOUT_MS` + 5 s = 65 s | `hook_heartbeat`（上位机心跳寄存器 0x04 变化） | 日志（错误码由 `hook_heartbeat` 自己写 0x01） |
| `bms` | 2 | **10 s**（2026-09-18 起） | `hook_bms`（**500 ms** 轮询中任一查询成功即打卡；软待机期间继续轮询） | 日志 + 错误码 0x04（由健康回调置位） |
| `alarm_module` | 3 | **15 s** | `hook_alarm`（音量变化时立即通讯；音量不变时每 **3 s** 幂等保活通讯） | 日志（错误码 0x02 由 `hook_alarm` 写） |

（`modem_4g` 事件已于 2026-09-17 删除：4G 链路的存活已由 `host_heartbeat` 覆盖，
4G 线程自身仍参与 `task_alive` 打卡。详见第 8 节。）

* 健康事件只做**日志与告警**，不直接改错误码寄存器（113）——该寄存器仍由检测到
  故障的模块单独写自己的位，保证“一位一个写者”（这是上一轮确定的规则）。
* 掉线/恢复会打印 `field event xxx offline/online`，可用
  `sys_health` 的 shell 命令查看统计（`CONFIG_SYS_HEALTH_SERVICE_SHELL=y`）。
* 本轮变化：GPS 事件（原 ID 4）已随 GPS 移除；任务打卡的位 `1<<3` 由 GPS 线程
  改为 RTC 线程（`HOOK_TASK_ALIVE_RTC`），打卡集合仍是 5 位。

### 1.2 模块自带的内核级检查（按当前 `prj.conf`）

| 检查项 | 开关（本工程取值） | 说明 |
| --- | --- | --- |
| 事件核心 | `CONFIG_SYS_HEALTH_SERVICE=y` | 事件注册、离线判定、动作状态、100 ms 巡检 |
| 栈用量检查 | `SYS_HEALTH_STACK_USAGE_CHECK=y`（30 s） | 扫描所有线程栈的未使用量/占用率（阈值 128 B 或 80%），只告警 |
| 复位动作后端 | `SYS_HEALTH_REBOOT_ACTION_BACKEND=y`（250 ms） | 有事件请求 `REQUEST_REBOOT` 时执行冷复位 |
| 硬件看门狗喂狗 | `SYS_HEALTH_WATCHDOG_FEED_BACKEND=**n**` | **当前是关闭的** |
| ICMP 探测 | `SYS_HEALTH_ICMP_PROBE=n` | 本产品无以太网 |
| 健康灯指示后端 | `SYS_HEALTH_LED_INDICATOR_BACKEND=y`（2026-10-27 启用） | 心跳灯改由健康事件驱动，原 `hook_supervisor` 的 LED 线程已删除 |
| 定时健康复位 | `SYS_HEALTH_SCHEDULED_REBOOT=n` | 未启用（“每天 4 点复位一次”的策略） |

> **需要决策的一点**：喂狗后端关闭时 `wdt_setup()` 不会被调用，IWDG 根本不会启动，
> 因此 `task_alive` 超时目前只有日志与告警，**不会复位设备**。IWDG 的复位依赖
> `CONFIG_SYS_HEALTH_WATCHDOG_FEED_BACKEND=y`（该后端同时决定 `SYS_HEALTH_WDT_TIMEOUT_MS`
> 与喂狗周期）。若要恢复“任务卡死 → 30 s 后复位”的行为，把这一项改为 `y` 即可，
> 代码路径不变（`hook_health_ota_gate()` 仍会在 OTA 期间暂停打卡监督）。

### 3.2 RTC 寄存器拆分（第 3.1 / 3.2 条）

旧实现：只有一个保持寄存器 `RTC_TIME`(114)，既是校准输入又是时间显示，且只有
时分（没有年月日）。新实现参考 `craner_ai_safety_car`，拆成两组：

| 组 | 寄存器 | 方向 | 内容 |
| --- | --- | --- | --- |
| 校准（一次性命令） | 保持 H0x20 / H0x21 / H0x22 | 上位机 / 云端 → 本机 | 年 / 月+日 / 时+分（北京时间） |
| 显示（当前时间） | 输入 I0x10 / I0x11 / I0x12 | 本机 → 上位机 / 云端 | 年 / 月+日 / 时+分（北京时间） |

* 命令默认值 `0 / 0 / 0xFFFF` 表示“未写入”（0 不是合法年/月日；00:00 合法所以
  时分用 0xFFFF 表示未写入）。
* 三个寄存器可以一次 FC16 写，也可以分三条 FC06 写；全部离开默认值且数值合法
  才执行，避免半条命令生效。
* 只写一半的命令 60 s 后自动清空并告警（防止“很久以后补上后两字节”造成误校准）。
* 秒不参与校准（产品对时间精度要求不高），校准值总是整分。

### 3.3 时间同步与信任建立（第 3 条正文）

两条路径最终走同一条流水线，都是“先写校准寄存器，再同步 RTC，再由
`time_manager_service` 建立信任”：

```text
上位机 Modbus RTU ─┐
                   ├─→ H0x20/0x21/0x22（一次性命令）
云端 0xA5 0x09 ────┘            │
                                 ▼
                   app/hook_rtc 线程（每秒检查）
                   校验 → rtc_set_time() → 秒置 0
                        → rtc_trust_store_mark_valid(MANUAL)
                        → time_source_rtc_refresh()
                        → 清空命令寄存器 → 刷新 I0x10..0x12
```

* 云端 0x09 的载荷从“2 字节 hh:mm”扩展为 **6 字节**（年、`(月<<8)|日`、`(时<<8)|分` 三个小端 u16，与校准寄存器逐字对应），
  否则无法校准年月日。协议文档已同步（`docs/AISatefy-Hook-MQTT通信协议-v2.0.0.md` 6.8 节）。
* 未校准（trust 无效）时：定时关机 / 硬待机都不执行，只打印
  `no trusted RTC time yet, waiting for a host or cloud calibration`。
* 调试命令：`hook rtc` 查看状态，`hook rtc set 2026-09-16 14:30` 写校准，
  `hook status` 看整体。

### 3.4 定时开关机 / 休眠功能完善（第 3.3 条）

在旧 `hook_rtc.c` 基础上重写为 `app/hook_rtc/hook_rtc.c`：

| 行为 | 说明 |
| --- | --- |
| 关机窗口 | `[H0x11 关机时间, H0x10 开机时间)`，北京时间，支持跨零点（21:00→次日 06:00） |
| 软待机 | 进入：清灯光/声光命令、切断声光供电、`PWD_LED` 灭、工作模式 0；**BMS 继续轮询且健康检测保持有效**，声光/上位机心跳两个健康事件暂停；离开：恢复供电与这两个事件 |
| 硬待机 | `STM32_STANDBY_ENABLE`(0x12)=1 时（**与 0x13 软待机使能无关**），先关断输出，再按 0x10 设 RTC Alarm B（UTC 编程）并进入 STANDBY；Alarm B 唤醒后回正常流程 |
| 判据 | 用**区间判断**而不是“精确分钟触发”：设备在关机时段内重启会立即回到待机（参考工程用精确分钟触发，存在“重启后整晚不复位”的漏洞） |
| 频率 | 线程 1 s 循环（校准检查 + 时间发布），调度判定 5 s 一次 |
| 持久化 | H0x10/H0x11 标记 `PERSISTENT`，保存到 W25Q64 的 `modbus-store` 分区，复位/掉电/OTA 后保留；`modbus_data save/load/status` 可手工干预 |
| 前置条件 | 必须有 trust 有效的时间；无时间不动作 |

配置项：`CONFIG_HOOK_POWER_ON_TIME_HHMM=1536`(06:00)、
`CONFIG_HOOK_POWER_OFF_TIME_HHMM=5376`(21:00)、`CONFIG_HOOK_HARD_STANDBY_ENABLE=y`。
硬待机还要求选项字节把 IWDG 在 Standby 下冻结（见 README 注意事项 3）。

## 4. 寄存器表改用 `modbus_data_model` 子模块

**可以，而且已经实现。** 之前的实现是两张 256 项的裸数组
（`app/hook_modbus/hook_register.c`），没有名称、权限、默认值，也不能持久化；
现在与参考工程 `craner_ai_safety_car` 用同一个子模块承载。

### 4.1 改了什么

1. **新增子模块** `module/modbus_data_model`（提交 `53f6aa37`，与参考工程一致），
   离线从参考工程的 `.git/modules` 复制并登记 gitlink，`.gitmodules` 已更新。
2. **寄存器表**（`app/hook_modbus/hook_register.c`）：把本产品用到的寄存器写成
   带名称/地址/默认值/权限的表（2026-09-17 起按读写方向重排：保持=云端写、
   输入=云端读，见 [寄存器映射.md](寄存器映射.md)）；H0x10/H0x11 标记
   `MODBUS_REG_ACCESS_RW_PERSISTENT`。
3. **RTU 从机接口**：`component/am_modbus` 增加可选的寄存器读写回调
   （`reg_read_cb` / `reg_write_cb` / `input_read_cb`），`hook_modbus_slave_init()`
   把三张表接到从机，FC03/FC04/FC06/FC16 直接读写数据模型，不再有第二份副本。
   未设置回调的从机（例如两台 RTU 主机）行为与原来完全一样。
4. **持久化**：`modbus_data_model_store` + flash 后端，分区 `modbus-store` 在
   板载 W25Q64 QSPI Flash（偏移 0x20000，8 KiB；详见第 7 节的迁移记录）。
   保存采用“双 bank + CRC + 3 s 延迟写”的通用结构。
5. **产品 API 不变**：`hook_reg_get/set/set_bits/error_bits` 保留（内部改为访问
   数据模型），所以 `hook_alarm` / `hook_bms` / `hook_heartbeat` / `hook_work_mode` /
   `hook_cloud_proto` / shell 都不用改逻辑；新增 `hook_reg_input_get/set` 用于
   输入寄存器（当前时间显示）。
6. **调试**：`modbus_data status|save|load|clear`；`hook reg <n>` 读写保持寄存器、
   `hook reg i<n>` 读写输入寄存器。

### 4.2 行为差异（需要注意）

| 项目 | 旧（裸数组） | 新（数据模型） |
| --- | --- | --- |
| 未定义地址读 | 返回数组里的残值（一般是 0） | 返回 0 |
| 未定义地址写 | 存进数组（无意义） | 忽略（调试日志 `LOG_DBG`） |
| 定时开关机时间 | 每次上电回默认值 | 持久化，掉电保留 |
| 线圈 FC01/05/15 | 借用保持寄存器位 | 不参与协议，用 16 字影子数组兜底（不会崩溃，恒为 0） |
| RAM 开销 | 2 × 256 × 2 B = 1 KiB | 表 27 项（24 保持 + 3 输入）约 0.5 KiB + 只读名称字符串 |

如果上位机确实用到了本表之外的保持寄存器，告诉我地址和含义，加一行即可。

### 4.3 持久化的位置（2026-09-17 已迁到 QSPI）

最初 store 放在内部 Flash 最后一个 128 KiB 扇区，H7 内部 Flash 的最小擦除单位
也是 128 KiB，两个 64 KiB bank 会落在同一扇区（等效单 bank）。现已按参考工程
`craner_ai_safety_car` 的做法把 store 迁到**板载 W25Q64 QSPI NOR Flash**：

* `modbus-store` 分区 = QSPI 偏移 0x20000、8 KiB；W25Q64 的擦除单位是 4 KiB，
  两个 bank 各自正好一个扇区 → **真正的双 bank**，保存途中掉电只会退回上一份值。
* 内部 Flash 恢复为纯固件布局（mcuboot / slot0 / slot1 / coredump / app-storage），
  不再有运行时写入内部 Flash 的分区。
* 保存动作仍在系统工作队列里执行（3 s 延迟 work），不占用 RTC / Modbus / 4G /
  日志线程；MCUmgr 有独立工作队列。
* 仍建议不要把 0x10/0x11 当"高频可写寄存器"用（每次变化触发一次擦写）。
* QSPI 上还预留了 `param-store`（128 KiB，给后续 `device_param_server`/Settings）
  和 `reserve`（~8 MiB，给离线日志）。

## 7. 复查修正（2026-09-17）

针对汇总 1 落地后的 5 个复查问题：

### 7.1 打卡语义：线程存活，而不是"有活干"

原实现里 `hook_alarm`（`if (is_soft_standby != 1U)` 才打卡）和 `hook_bms`
（软待机时 `continue` 跳过打卡）在软待机期间**不再打卡**，12 s 后 `task_alive`
事件离线；如果打开喂狗后端（`CONFIG_SYS_HEALTH_WATCHDOG_FEED_BACKEND=y`），
正常的软待机会被当成线程卡死而复位设备。4G 线程 `hook_4g` 则是每轮循环都打卡
（与是否收到网络数据无关），RTC/心跳线程同理。

修正：**所有业务线程把打卡移到循环最顶部、无条件执行**（`hook_alarm` / `hook_bms`
已改，`hook_rtc` / `hook_4g` / `hook_heartbeat` 本来就是），并把规则写进
`app/hook_health/hook_health.h` 与 `src/system_def.h` 的注释：

> 打卡 = 该线程在跑；模式相关的暂停必须用 `hook_health_sleep_update()` /
> `hook_health_ota_gate()` 表达，不允许用"跳过打卡"来表达。

### 7.2 硬待机不再依赖软待机使能

原判断 `(hard_enable == 1U) && (soft_enable == 1U)` 让 `STM32_STANDBY_ENABLE`
被 `SOFT_STANDBY_ENABLE` 绑架。现在两者独立：

* 关机时段内 `STM32_STANDBY_ENABLE`(0x12)=1 → 关断输出（清声光命令、切
  `ALARM_POWER_EN`、灭 PWD_LED、暂停现场健康事件）→ 设 RTC Alarm B → 进 STANDBY；
* 只有 `SOFT_STANDBY_ENABLE`(0x13)=1 → 仅软待机；
* 两个都为 0 → 不做任何休眠（若之前处于软待机则退出）。

### 7.3 `modbus-store` 迁到板载 QSPI Flash

见 4.3 节。dts 新增 `&quadspi` + W25Q64 节点与 `param-store` / `modbus-store` /
`reserve` 三个分区（布局与小车一致），内部 Flash 恢复 `app-storage`。

### 7.4 `hook_relay` → `hook_heartbeat`，并清点全部 "relay" 命名

板上**没有继电器**：PE5 是声光报警的供电使能（.ioc 里叫 `FLASH_LIGHT_POWER_EN`，
原理图上标注"警报灯供电使能"）。因此两处 relay 命名都改掉了，涉及的位置全表如下：

| 位置 | 旧 | 新 |
| --- | --- | --- |
| 模块目录/文件 | `app/hook_relay/hook_relay.{c,h}` | `app/hook_heartbeat/hook_heartbeat.{c,h}` |
| 线程名 | `RelayHeartbeat` | `HostHeartbeat` |
| 日志模块 | `LOG_MODULE_REGISTER(hook_relay)` | `hook_heartbeat` |
| Kconfig | `CONFIG_HOOK_HEARTBEAT_RELAY_ENABLE` | `CONFIG_HOOK_HOST_HEARTBEAT_ENABLE` |
| 打卡位 | `HOOK_TASK_ALIVE_RELAY` | `HOOK_TASK_ALIVE_HEARTBEAT` |
| dts 别名/节点 | `relay-en` / `relay_en`（label `FLASH_LIGHT_POWER_EN`） | `alarm-power-en` / `alarm_power_en`（label `ALARM_POWER_EN`） |
| board.h | `relay_en_gpio` | `alarm_power_en_gpio` |
| 上位机心跳寄存器 | `STATUS_HEART_BEAT`(104) | `CMD_HOST_HEARTBEAT`(0x04，可写所以归保持寄存器) |
| 日志/注释/文档 | "relay on/off" | "alarm power on/off" |

`hook alarm`、`hook status`、`hook reg` 等命令名不受影响；`app/hook_alarm` 里的
`ERR_LED_OFFLINE`、`LED` 等命名与继电器无关，保持不变。

### 7.5 状态寄存器迁到输入寄存器

见 [寄存器映射.md](寄存器映射.md)：保持寄存器只剩"云端/上位机要写的东西"，
状态与遥测全部搬到输入寄存器（对外只读），地址重新分配：

| 组 | 保持寄存器（写） | 输入寄存器（读） |
| --- | --- | --- |
| 命令 | 0x00 灯光 / 0x01 7 m / 0x02 3 m / 0x03 音量 / 0x04 上位机心跳 | — |
| 配置 | 0x10 开机 / 0x11 关机 / 0x12 硬待机 / 0x13 软待机 / 0x14 心跳使能 | — |
| RTC | 0x20 年 / 0x21 月日 / 0x22 时分（校准命令） | 0x10 年 / 0x11 月日 / 0x12 时分（当前时间） |
| 状态 | — | 0x00 工作模式 / 0x01 错误码 / 0x02 灯光 / 0x03 喇叭 / 0x04..0x0A BMS |

云端协议（0xA5）按名字访问寄存器，未受影响；Modbus RTU 调试脚本需要按新地址表更新。

## 8. 复查修正之二（2026-09-17，健康检测语义）

### 8.1 软待机时还检测离线吗？

* **线程打卡（`task_alive`）仍然检测**：软待机不关闭任务打卡监督，只关"现场设备"事件。
  由于 7.1 已让所有线程在循环顶部无条件打卡，软待机不会再被误判为线程卡死。
* **声光 / 上位机心跳两个现场事件在软待机期间被关闭**
  （`hook_health_sleep_update(true)` → `sys_health_event_disable()`），期间不再判离线、
  不再上报；退出软待机时重新使能并立刻补一次"在线"上报，所以不会残留离线状态。
  **BMS 不在这个列表里**（2026-09-18 修正）：CubeMX 固件在软待机期间也一直轮询 BMS
  （`modbus_bms_handle()` 没有待机判断），所以本工程同样保持轮询，其 **10 s** 离线判定
  在软待机期间照常生效。
* 依据：`module/system_health_service/system_health_event.c` 的 `sys_health_event_disable()`
  会清 `enable/offline_status/offline_since_ms`，事件不再参与离线判定。

### 8.2 BMS：判定统一为"10 s 无成功通讯"，500 ms 轮询也计入

原来只有 10 s 的慢轮询里上报，而 500 ms 快轮询（剩余充放电时间/保护状态）虽然一直在
通讯却不上报；而且错误码 `ERR_BMS_READ_FAIL` 是**单次**电量读取失败就置位（一次丢帧就把
工作模式打成"故障"）。现在：

* 线程每轮记录"本轮是否有任一查询成功"（500 ms 与 10 s 两条路径都算），成功即
  `hook_health_report(HOOK_HEALTH_EVENT_BMS)`；
* 判定交给健康服务：`bms` 事件的 **10 s** `offline_timeout_ms`（2026-09-18 从 25 s 收紧）内没有成功上报 → 判离线，
  由 `hook_health_offline_first()` 回调置 `ERR_BMS_READ_FAIL`；恢复时由
  `hook_health_online_first()` 回调清位（见 8.7）；
* 模块自身不再维护"最后成功时间"，也不再有第二次判定。

### 8.3 声光报警器：3 s 保活通讯 + 15 s 超时

原来只有在音量寄存器变化或灯光切换时才与声光模块通讯，安静运行时长时间无通讯 →
误报离线。现在 `hook_alarm_volume_sync()` 承担全部存活检测：

* 音量值**变化** → **立即下发，不受任何限速**（新值必须马上到模块）；成功即上报在线；
* **无论音量变没变，两次通讯间隔最多 3 s**：每次通讯（下发音量或保活）都会重置 3 s 计时，
  保活是**把当前音量值再写一遍**的幂等写，成功即上报在线
  （选择写而不是读：模块的寄存器读功能没有手册保证，写是我们本来就在用的通道）；
* 只有"**同一个值发送失败后的重试**"限速为每秒一次：模块无响应时一次 Modbus 尝试要阻塞
  本线程约 1 s（`MODBUS_WAIT_TIMEOUT_MS`），重试更快只会拖慢闪烁节拍、刷爆 485 总线；
* 通讯失败只**记录日志**；判定由健康服务负责：`alarm_module` 事件的 **15 s**
  `offline_timeout_ms` 内没有成功上报 → 判离线，回调置 `ERR_LED_OFFLINE`；任意一次成功
  → 上报在线，回调清位（见 8.7）。
* 离线超时从 25 s 收紧到 **15 s**（3 s 保活 × 5）。
* 灯光控制路径（`hook_alarm_led_logic`）与音量/保活路径共用
  `hook_alarm_report_online()`／`hook_alarm_log_failure()` 两个帮助函数，成功/失败语义一致。

### 8.4 删除 4G 离线事件

删除了 `HOOK_HEALTH_EVENT_4G`（事件表条目 + `hook_4g.c` 里的上报调用）：4G 链路是否通，
最终由"能不能收到上位机心跳帧"体现，即已有的 `host_heartbeat` 事件；4G 线程自身仍在
`task_alive` 打卡集合里，所以"线程卡死"依然能被发现。

### 8.5 / 8.6 关于"停喂狗重启"与重启次数限制（当前行为）

**当前只有 `task_alive` 会停喂狗**（`action_mask` 含 `SYS_HEALTH_ACTION_STOP_WATCHDOG_FEED`）：
只有"业务线程打卡缺失"才会停喂狗 → IWDG 复位。BMS / 声光 / 上位机心跳这三个**现场设备**
事件只有 `SYS_HEALTH_ACTION_LOG`，**离线只记录日志与错误码，不会重启设备** —— 这一点和
"某些检测只记录、某些检测可重启"的需求天然一致：改 `action_mask` 即可切换某类检测的处置方式。

**重启次数限制目前没有**，而且 `watchdog_feed_stop_requested` / `reboot_requested_latched`
在 `system_health_service` 里是**只置位不清除**的 latch，一旦触发就只能靠复位恢复，
所以"同一原因最多重启 3 次"需要新增一层应用侧策略，建议做法（待确认后实现）：

1. 在保留存储（板载 W25Q64 的 `param-store`，或 BBRAM 里 `rtc_trust_store` 记录之后的空闲区）
   保存"原因 → 重启计数 + 首次时间戳"；
2. 应用在每次触发停喂狗前先累加并立即落盘（`modbus_data_model_store_save_now()` 或直接写 BBRAM）；
3. 开机时读计数：同一原因已达 3 次，则用 `sys_health_event_register()` 把该事件的
   `action_mask` 改成"只记录 + 置降级"（去掉 `STOP_WATCHDOG_FEED`），本次开机不再复位，
   设备带故障运行并持续上报；
4. 连续正常运行 N 分钟（例如 30 min）后清零计数，避免"修好之后永远不复位"。

需要你确认：计数放 BBRAM 还是 QSPI、时间窗与清零条件、"哪些原因计入上限"（目前只有
`task_alive` 能复位），确认后我再实现。

### 8.7 在线/离线判定归属：服务判定，回调执行副作用

两者原本职责不同，所以历史上是两套独立判定：

| | 错误码（输入寄存器 0x01 的位） | 健康事件（`system_health_service`） |
| --- | --- | --- |
| 面向 | 现场诊断：心跳灯闪烁次数、云端 0xF0/0x06 字节、工作模式 | 运行观测与动作策略：`offline_count`、离线时长、日志、是否停喂狗/复位 |
| 判定来源 | 检测模块自己（"谁检测谁写"） | 服务内的"最后上报时间 + offline_timeout_ms" |
| 历史 | 旧 CubeMX 固件的故障码 | 本次重构引入的复用服务 |

中间版本曾经让轮询模块自己数"连续 N 次失败"并同时置错误码 + 上报离线，那是走反了：
`system_health_service` 的设计本来就是**服务做判定（`offline_timeout_ms` + 上报时间戳），
事件的 `offline_first_func` / `online_first_func` 回调执行后果**。参考工程
`craner_ai_safety_car` 的注释写得很明确：

> "Health callbacks are the single owner of the readable/error state registers.
> Polling threads only report successful reads/probes and update measured input values;
> they no longer toggle online/offline coils."

现在本工程按这个约定重写（2026-09-17 第三版）：

* **轮询模块只上报成功**：`hook_health_report(HOOK_HEALTH_EVENT_xxx)`，不再自带计时器、
  不再自己置错误码；
* **服务做唯一判定**：事件 `offline_timeout_ms` 内没有任何"成功上报"即判离线；
* **事件回调执行后果**：`hook_health_offline_first()` / `hook_health_online_first()`
  （在 `app/hook_health/hook_health.c`）是**错误码位的唯一所有者**，置/清
  `ERR_BMS_READ_FAIL`、`ERR_LED_OFFLINE`、`ERR_HEARTBEAT_TIMEOUT` 并打日志。

```c
/* 轮询模块：只有这一句 */
hook_health_report(HOOK_HEALTH_EVENT_BMS);     /* 每次成功通讯 */

/* 健康服务回调：判定成立时执行后果 */
static void hook_health_offline_first(const struct sys_health_event_status *st)
{ ... hook_reg_set_error_bits(ERR_BMS_READ_FAIL); ... }
static void hook_health_online_first(const struct sys_health_event_status *st)
{ ... hook_reg_clear_error_bits(ERR_BMS_READ_FAIL); ... }
```

判定阈值就是事件自己的 `offline_timeout_ms`，全工程只有一处：

| 事件 | `offline_timeout_ms`（唯一判定） | 轮询节奏 |
| --- | --- | --- |
| `alarm_module` | **15 s** | 音量变化立即发；不变时 3 s 保活 |
| `bms` | **10 s** | 500 ms 快轮询 + 10 s 慢轮询，任一成功即上报；软待机期间不停 |
| `host_heartbeat` | **65 s**（`HEARTBEAT_TIMEOUT_MS` 60 s + 5 s 余量） | 上位机心跳计数器变化即上报；60 s 切断声光供电是模块自身的动作 |
| `task_alive` | 12 s（线程打卡窗口） | 5 个线程循环顶部无条件打卡 |

保留在模块自身、但**不属于离线判定**的逻辑：

* `hook_alarm`：1 s 重试限速（传输节奏，避免阻塞线程/刷总线）、3 s 保活；
* `hook_heartbeat`：60 s 静默时切断声光供电、心跳恢复时重新供电（产品动作，与判定阈值一致）；
* `hook_bms`：读取失败时把电量显示清零（测量值语义）；
* `hook_rtc`：进入软待机时清心跳/声光故障位（产品动作）。

下面是中间版本的记录，保留以便对照：

**（历史）合并为一个判定点**：由检测模块判定（它最清楚该用几次失败、多长时间），判定成立时
同时做两件事：

```c
hook_reg_set_error_bits(ERR_xxx);                     /* 现场诊断：错误码 */
hook_health_report_offline(HOOK_HEALTH_EVENT_xxx);    /* 统计 + 动作策略 */
```

任意一次成功通讯时成对恢复：

```c
hook_reg_clear_error_bits(ERR_xxx);
hook_health_report(HOOK_HEALTH_EVENT_xxx);
```

实现上 `hook_health_report_offline()` 调用服务的 `sys_health_event_set(event, true)`
（`manual_offline`），而下一次 `hook_health_report()` 会自动清掉它
（`sys_health_event_report()` 会清 `manual_offline`）。因此**错误码置位的那一刻，
健康事件同步离线**（统计、日志、动作策略一起走），不再有两套计时器。

各模块的判定点（错误码与健康事件共用同一判据）：

| 事件 | 判定点 | `offline_timeout_ms` 的角色 |
| --- | --- | --- |
| `alarm_module` | 连续 3 次与声光模块通讯失败（约 3 s） | 15 s 兜底（完全没有判定上报时） |
| `bms` | 10 s 内没有任何一次成功通讯 | 10 s 兜底（同上）；软待机期间同样生效 |
| `host_heartbeat` | 上位机心跳计数器 60 s 不变 | 65 s 兜底（同上） |
| `task_alive` | 业务线程打卡缺失（12 s 窗口） | 本身即判定（没有独立错误码位） |

这样"哪些检测只记录、哪些检测复位"仍只由事件的 `action_mask` 决定（见 8.5/8.6），
而"什么时候算离线"只有一个地方说了算。

### 8.8 PWD_LED(PB3) 的全部驱动路径（对齐原固件）

原固件 `application/app_relay.c` 在 60 s 心跳超时分支里**同时**拉低两个引脚：

```c
HAL_GPIO_WritePin(FLASH_LIGHT_POWER_EN_GPIO_Port, FLASH_LIGHT_POWER_EN_Pin, GPIO_PIN_RESET);
HAL_GPIO_WritePin(PWD_LED_GPIO_Port, PWD_LED_Pin, GPIO_PIN_RESET);
```

之前本工程的移植只做了"清 `CMD_LED_SWITCH`"，靠 `hook_alarm` 每 50 ms 的镜像把 PWD_LED
带灭 —— 效果对，但**不是同一次动作**，而且声光模块被编译掉时就没有人驱动这个脚了。
现在 `hook_heartbeat` 在 60 s 超时分支里直接补上 `GPIO_WRITE(pwr_led_gpio, 0)`。

| 场景 | 原固件 | 本工程（现在） |
| --- | --- | --- |
| 上电初始化 | `PWD_LED` RESET | `board_gpio_init()` 低 + `hook_heartbeat_init()` 写 0 |
| 灯光功能开启 | `led_logic()` 每次镜像 `CMD_LED_SWITCH` | `hook_alarm_led_logic()` 每 50 ms 镜像 |
| 静默 >10 s | 清 LED/声光命令寄存器 | 同 |
| **静默 >60 s** | PE5 RESET **+ PWD_LED RESET** + 置 `ERR_HEARTBEAT_TIMEOUT` | PE5 关 + **PWD_LED 写 0** + 清命令；错误码由健康服务回调置位 |
| 心跳恢复 | PE5 SET、`last_volume=0xFFFF`、`STATUS_LED_SWITCH=0` | 供电恢复、音量强制同步、`STATUS_LED_SWITCH=0`（PWD_LED 仍跟随 `CMD_LED_SWITCH`=0） |
| 上电自检（POST） | 播放测试音时 SET，结束 RESET | 同 |
| 软待机进入 | PE5 RESET + PWD_LED RESET + 清心跳/声光错误位 | 同（`hook_rtc_sleep_enter()`） |
| 软待机退出 | PE5 SET（PWD_LED 不写，跟随命令寄存器=0） | 同 |

> 与原固件一致的一点：PWD_LED 最终仍以 `CMD_LED_SWITCH` 为准。所以如果上位机心跳已经丢失、
> 但**云端又通过 4G 把灯光命令写成 1**，PWD_LED 会再次点亮（原固件也是这个行为）。
> 若希望"上位机心跳丢失期间 PWD_LED 一直被闩死为灭"，把 `hook_alarm_led_logic()` 里的镜像
> 条件改成 `cmd_led_switch == 1 && hook_heartbeat_alarm_power_is_on()` 即可 —— 需要的话告诉我。

### 8.9 与原固件的控制逻辑差异复查（2026-09-18，逐条确认结论）

复查共列出 15 项差异，本轮按确认结果处理如下：

| # | 差异 | 结论 / 处理 |
| --- | --- | --- |
| 1 | BMS 在软待机时是否轮询 | **改为与原程序一致：继续轮询**（`hook_bms` 去掉软待机跳过），同时把 BMS 从"软待机暂停的健康事件"列表里移除，10 s 离线判定在待机期间照常生效 |
| 2 | 声光 LED 关闭重试限速 | 保留 1 s 限速（防刷总线/防拖慢闪烁节拍，属传输节奏而非判定） |
| 3 | 心跳超时错误码的置位时刻 | 保留 65 s 判定（60 s 切供电 + 5 s 余量），避免上位机正好 60 s 发一次时在边界抖动 |
| 4 | BMS 离线超时 | **改为 10 s**（`HOOK_HEALTH_BMS_TIMEOUT_MS`） |
| 5 | 硬待机触发方式 | 保留区间判断（设备在关机时段内重启也会进待机） |
| 6 | 进硬待机前是否切断声光供电 | 保留"先切断再进 STANDBY"（见 8.10 对 STANDBY/GPIO 的说明） |
| 7 | 硬待机失败重试 | **改为重试**：删掉 `hard_standby_armed`，`pwr_enter_standby()` 返回（未能进入）后每 5 s 重试，与原程序每秒重试的语义一致 |
| 8 | 调度检查周期 | 保留 5 s（分钟级调度足够） |
| 9 | 0x09 时间命令帧 | **改为全部小端**：3 个 `uint16` 字段（年、`(月<<8)|日`、`(时<<8)|分`），共 6 字节，与校准寄存器逐字对应；长度错→`0x02`，数值越界→`0x04` |
| 10 | 非 usr.cn# 纯文本帧是否镜像到 MQTT | 保留（便于远程调试看模块输出） |
| 11 | AT+OTAREQUEST / AT+OTABOOT 语义 | 见 8.11；两者在本工程都只是"武装应用内 Ymodem 接收器" |
| 12 | AT+OTAINFO 载荷 | 保留 MCUboot 信息格式（上位机需同步改） |
| 13 | IWDG 超时值 | 统一 **30 s**：健康喂狗后端用的 `CONFIG_SYS_HEALTH_WDT_TIMEOUT_MS` 模块默认就是 30000 ms；`IWDG_STM32_INITIAL_TIMEOUT` 不能写 30000（Kconfig 上限 26214，按 LSI 最坏 40 kHz 估算），已改为注释说明 |
| 14 | 未定义寄存器地址 | 保留稀疏表（读 0、写忽略），调试脚本按新表更新 |
| 15 | 4G 分帧判据（DMA+硬件 IDLE vs 20 ms 软件空闲） | 见 8.12；保留软件空闲方案 |

### 8.10 STANDBY（深度睡眠）到底发生了什么

`pwr_enter_standby()`（`src/pwr_stm32.c`）设置 `PWR_CPUCR_PDDS_D1/D2/D3` + `SLEEPDEEP`
后执行 `WFI`，即进入 **STM32H7 的 STANDBY 模式**，它是该芯片最深的低功耗模式：

* **MCU 不再运行**：VCORE 掉电、所有时钟（除 RTC/LSE 与备份域）停止、SRAM 与寄存器内容丢失，
  没有代码在执行；只有 WKUP 引脚、RTC Alarm、IWDG 复位、NRST 能把它唤醒。
* **唤醒后是一次完整的系统复位**：从 BootROM/复位向量重新启动（这也是代码里用
  `pwr_wakeup_from_standby()` 区分"待机唤醒 / 冷启动"的原因），所有外设、GPIO、线程都会重新初始化。
* **GPIO 不保持睡眠前的电平**：进入 STANDBY 后 I/O 输出级失去供电，引脚变成**高阻**，
  之前的驱动电平不会维持；此时引脚电平由**外部电路**（上下拉电阻、负载开关的默认状态）决定。
  只有备份域相关引脚（如 PC13/PC14/PC15 视配置）例外。
  因此：
  * 进待机前把 `ALARM_POWER_EN`(PE5)/`PWD_LED`(PB3) 拉低，只能保证**进入前**和**唤醒后**的状态；
    待机期间若这两个负载必须保持关断，硬件上需要**下拉电阻**（或负载开关自身默认关断）。
  * 这也意味着原固件"不写 PE5 就进待机"和我们"先拉低再进待机"在**待机期间**的最终电平其实一样
    （都由外部电路决定），差别只在进待机前那一瞬间。
  * 本工程板上 PE5/PB3 的外部上下拉我无法从现有资料确认（hook 载板原理图不在仓库里，
    只有通用核心板原理图），建议上板实测：进待机后用万用表量 PE5/PB3 与警报灯供电的实际电平。
* 唤醒后 `board_gpio_init()` 会把 PE5 重新打开（与原固件一致：唤醒等同冷启动）。

### 8.11 为什么 AT+OTAREQUEST / AT+OTABOOT 与原程序语义不同

原程序的 OTA 是**自定义 bootloader**：`AT+OTAREQUEST` 只写 flash meta 里的"ota_request"标志，
`AT+OTABOOT` 写标志后**立即复位**，由 bootloader 在启动时进入接收流程（Ymodem 下载由
bootloader 完成）。本工程改成 **MCUboot + 应用内 Ymodem**：

* MCUboot 本身不做串口/Ymodem 接收（`MCUBOOT_SERIAL` 是另一套串口恢复协议，且需要独占串口），
  固件是通过 4G 模块的 MQTT 话题 2 进来的，只能在**应用内**接收并写 slot1；
* 所以"复位进 bootloader 再下载"这条路在本工程不存在：`AT+OTAREQUEST` 和 `AT+OTABOOT`
  都简化为"武装应用内 Ymodem 接收器并回 `craner#OK`"（不再复位）；
* 上位机如果依赖 OTABOOT 后的"设备重启"来同步状态，需要改成等到 `craner#+OTASTATE:`/
  进度消息或 `DONE` 再判断；或者我们也可以给 OTABOOT 加一个"回 OK 后 200 ms 冷复位"的变体
  （但那会丢掉接收态，等于放弃这次 OTA）——不建议。

### 8.12 为什么 4G 分帧没有沿用 DMA + 硬件 IDLE

原程序用的是 CubeMX 生成的 `HAL_UARTEx_ReceiveToIdle_DMA()`：DMA 搬运 + USART IDLE 中断
触发一次"帧结束"，粒度是**1 个字符空闲**（115200 下约 87 µs）。本工程用中断收 + 软件空闲定时器
（3.5 字符，4G 通道固定 20 ms），原因：

1. 本工程的 `component/uart_manage` 是从原组件移植的 Zephyr 版，Zephyr 的 UART 驱动没有
   CubeMX 那种"ReceiveToIdle DMA + 回调"接口；要用 DMA 得改成 Zephyr 的 **异步 UART API**
   （`uart_rx_enable()` + `UART_RX_IDLE`），而这块板子的 devicetree **没有给 usart1 配置 DMA
   通道**（原工程用的是 CubeMX 生成的 DMA 句柄），需要新增 DMA 控制器/通道节点并重新验证；
2. 硬件 IDLE 的粒度太细：usr.cn 模块转发网络数据时经常是**多段突发**，1 字符空闲会把一条
   消息拆成很多"帧"（原程序能容忍，因为它的回调是逐帧无状态处理的）；本工程按"一条消息"
   处理（topic 前缀路由 + 粘滞路由 + AT 应答按 OK/ERROR 重组），所以需要一个更长的帧间隔
   （4G 通道 20 ms）来把一条消息凑齐；
3. 若确实想回到 DMA + IDLE，可以做（异步 API + DMA 节点），但需要重新验证 4G/OTA/AT 三条路径，
   并按"碎片级"而不是"消息级"重写分发逻辑 —— 工作量与回归风险都不小，建议保持现状。

### 8.13 20 ms 分帧会不会丢帧 / 延迟？（2026-09-18 复查）

**延迟**（每帧的额外延迟，可叠加）：

| 环节 | 最坏耗时 | 说明 |
| --- | --- | --- |
| 4G 通道空闲判帧 | **20 ms** | 一帧的最后 1 字节到达后等 20 ms 无新字节才交给上层 |
| 4G 线程取帧 | **≤50 ms** | 线程用 `k_msgq_get(..., K_MSEC(50))` 等待，事件驱动，实际通常 <1 ms |
| 模块 AT 应答重组 | 到 `OK/ERROR` 为止，最多 3 s | 只影响"把整段应答打印出来"，不影响命令执行 |

结论：云端下发一条命令到本机开始处理的额外延迟约 **20–70 ms**；你关心的 MQTT 订阅/发布话题查询
（`hook usr mqtt_pub_tp` / `mqtt_sub_tp`）本身就是"发命令 → 等模块应答 → 打印"，应答会先按 20 ms
判帧、再按 OK/ERROR 重组，端到端一般 **50–100 ms**，不属于可感知的延迟。

**丢帧**：按数据类型分别看（2026-09-18 复查结论）：

| 数据类型 | 被 20 ms 拆成多帧时 | 结论 |
| --- | --- | --- |
| 云端 0xA5 帧（话题 3/4/0） | 逐字节状态机 + 0xA5 同步字节重同步 | 安全，拆帧不影响 |
| OTA（话题 2） | 收下后进 256 B 队列，由 `hook_ymodem_input_byte()` **逐字节**消费 | 安全；CRC 错会 NAK 重传 |
| 模块 AT 应答（`usr.cn#`） | 按 `OK/ERROR` 重组（3 s 超时） | 安全（这也是当初加重组的原因） |
| **云端下的 AT 命令（话题 1 文本）** | 粘滞路由**不覆盖话题 1**：拆帧后帧头可能被判为"不匹配" | ⚠️ 小概率风险：一条被拆开的 `craner#AT...` 前半会被当未知帧、后半会被当无前缀帧。命令都很短（一次 publish 一个突发），实际很难触发；如需彻底消除，可给话题 1 加"按行（到 CRLF）重组"缓冲 |
| AT 应答重组期间的无前缀云帧 | `hook_4g_at_active` 期间，无前缀帧会被拼进 AT 缓冲 | ⚠️ 小概率：只有"云帧被拆帧"且"同时有 AT 交换在进行"时才会误吞 |

**本次修掉的一个真实丢字节点**：`component/uart_manage` 的中断收包在 `rx_idx` 达到
`recv_buffer_size`（4G 通道 2048 B）后，会**静默丢弃**后续字节，直到出现 20 ms 空闲才交付
（既无计数也无日志）。原程序的 DMA 版在缓冲区满时会**直接触发回调**（`size == buffer size`），
不存在这类丢弃。现已改为一致的行为：缓冲满时先交付已收数据（回调只写环形缓冲 + 长度队列，
ISR 安全），再继续收，消除了"单突发 >2048 B 或连续 >2048 B 无 20 ms 间隔就丢尾部"这一类问题
（例如快速连续的下行 OTA 分片、超长模块配置转储）。

**其余缓冲**：4G 通道另有 8 KB 环形缓冲 + 32 条长度队列；溢出会计入 `hook_4g_rx_drops_isr`
并打日志（`4G receive overflow: N frame(s) dropped`）。只有在 4G 线程长时间阻塞（例如 OTA
写 slot1 的整扇区擦除）且期间持续有下行数据时才可能触发，OTA 侧由 Ymodem 重传兜底。

**可选加固**（需要的话我再做）：① 话题 1 命令行重组（~20 行）；② 4G 环形缓冲从 8 KB 提到
16~32 KB；③ 4G 接收缓冲从 2048 B 提到 4096 B；④ 切到 Zephyr 异步 UART + DMA（见 8.12，成本最高）。

### 8.14 上电 12 s 就报 `task_alive` 离线（现场日志定位，已修）

现场日志：

```text
[00:00:12.027] <wrn> system_health_service: Health event action: event=1 name=task_alive actions=0x00000015
[00:00:12.027] <err> system_health_service: System protect latched by event=1 name=task_alive
```

`0x15 = LOG(0x01) | SET_DEGRADED(0x04) | STOP_WATCHDOG_FEED(0x10)`，正是 `task_alive` 的动作掩码，
说明该事件在上电 12 s 被判离线。

**根因（本工程引入的启动时序 bug）**：判定是两层——

* 应用侧 `HookHealth` 线程每 1 s 汇总一次 5 个线程的打卡位，**只有 5 位全到才调用
  `hook_health_report()`**（"我还能跑"）；
* 服务侧 `system_health_service` 只看"距离上次 report 多久"，超过事件的 `offline_timeout_ms`
  （`HOOK_HEALTH_TASK_TIMEOUT_MS = 12 s`）就判离线并执行动作。

而 `HookHealth` 为了让最慢的线程（声光模块上电自检阻塞约 8 s）有时间起床，设了
`HOOK_HEALTH_BOOT_GRACE_MS = 20 s` 的启动宽限期，**这 20 s 内一次都不上报**。宽限期（20 s）
比事件超时（12 s）长，于是服务在上电 12 s 就"等不到心跳"，把 protect 状态与"停止喂狗"
动作**锁存**了。

**后果**：当前 `CONFIG_SYS_HEALTH_WATCHDOG_FEED_BACKEND=n`，所以只是置降级 + 打日志；
一旦打开喂狗后端，上电 12 s 就会停止喂狗、IWDG（30 s）复位；而 `watchdog_feed_stop_requested`
/ `system_protect_latched` 在服务里**只置位、不清除**（`system_health_action.c`）→ 每次上电
都走同一条路，**死循环重启**。

**修复**：启动宽限期内照常上报"在线"（语义是"监督尚未开始"），宽限期结束后再按"5 位是否到齐"
判定：

```c
if (hook_get_time_ms() - started_ms < HOOK_HEALTH_BOOT_GRACE_MS) {
        /* 监督尚未开始：保持事件在线，避免服务的 12 s 超时在启动阶段锁存动作 */
        hook_health_report(HOOK_HEALTH_EVENT_TASK_ALIVE);
        k_msleep(HOOK_HEALTH_CHECK_PERIOD_MS);
        continue;
}
```

**现场验证**：刷入新固件后上电，12 s 处不应再出现该日志；服务自带 shell 可查看：

```text
health status      # 总体状态（protect/degraded）
health events      # 所有事件：online/offline、超时、计数
health event 1     # task_alive 单条详情（last_update_ms、offline_count、离线时长）
health protect     # protect / reboot_requested / watchdog_feed_stop
```

注意：若设备当前跑的是修复前的固件，protect 位已锁存，**只能靠复位清除**；刷入新固件重启即可。
